QWEN3-8B JARVIS AGENT FOR NEXUS

============================================================
1. OVERALL GOAL
============================================================

The long-term objective is to make Qwen3-8B the reasoning and action brain of NEXUS.

This is NOT intended to be a simple chatbot.

This is NOT intended to be only a NEXUS knowledge bot.

This is NOT intended to be only an intent classifier.

The target is a general-purpose AI agent with NEXUS awareness and the ability to operate tools.

The desired interaction is:

USER
↓
QWEN
↓
UNDERSTAND REQUEST
↓
REASON
↓
DECIDE WHETHER TO ANSWER OR ACT
↓
PLAN
↓
SELECT APPROPRIATE TOOL(S)
↓
EXECUTE TOOL
↓
READ TOOL RESULT
↓
DECIDE NEXT STEP
↓
VERIFY
↓
CONTINUE IF NECESSARY
↓
FINAL RESPONSE

The long-term experience should feel similar to a JARVIS-style assistant.

The user should be able to communicate naturally instead of learning special commands.

Examples:

"Open this website."

"Search the web for the latest information about NVIDIA."

"Research this topic and summarize it."

"Create E:/test.py."

"Create a Python calculator at E:/test.py and test it."

"Open this project, find the bug, fix it and run the tests."

"Create a task in NEXUS."

"Show me my projects."

"Plan my week."

"Read this file and explain what is wrong."

"Research this topic and save the findings to a markdown file."

Qwen must eventually be able to determine what actions and tools are required.

============================================================

Qwen itself does NOT magically have access to:

- Windows
- filesystem
- terminal
- browser

- NEXUS APIs

- tool-call formatting
- argument selection
- multi-step behavior
- verification
- failure recovery
- NEXUS understanding
- answer-vs-action behavior

RUNTIME provides:

- actual tools
- actual permissions
- actual execution
- actual browser access
- actual filesystem access
- actual web access
- actual NEXUS access
- actual terminal access
- actual APIs

Never confuse the two.

4. EXISTING NEXUS ML CONTEXT
============================================================

NEXUS already has an ML Phase 10 system based on:

microsoft/deberta-v3-base

It was trained as an intent/routing classifier.

Known final Phase 10 information:

- Model: microsoft/deberta-v3-base
- Parameters: approximately 184.4M
- Intents: 14
- Dataset: 2,800 rows
- 200 examples per intent
- Train/validation/test split: 1,960 / 420 / 420
- Epochs: 5
- Training steps: 615
- Test accuracy: 0.9738
- Test macro F1: 0.9737
- Validation accuracy: approximately 0.9810
- Validation macro F1: approximately 0.9809

The existing DeBERTa system must NOT be deleted or replaced during the Qwen training phase.

Qwen is a separate model/training effort.

Do not automatically assume DeBERTa + Qwen must remain the final production architecture.

The architecture will be decided after Qwen evaluation.

7. ANSWER VS ACTION
============================================================

Qwen must learn the distinction between explaining something and actually doing something.

Example:

User:
"How do I create a Python file?"

→ Explain.

User:
"Create a Python file at E:/test.py."

→ Use filesystem tool.

User:
"Open Google."

→ Use browser tool if browser capability exists.

User:
"What is Google?"

→ Answer normally.

User:
"Research the latest NVIDIA GPUs."

→ Use web research tools when available.

User:
"How can I research NVIDIA GPUs?"

→ Explain.

9. TOOL EXECUTION RULE
============================================================

NEVER hallucinate tool execution.

If Qwen says:

"I created the file."

there must be an actual successful filesystem result.

If Qwen says:

"The tests passed."

there must be an actual test result.

If Qwen says:

"I searched the web."

there must be an actual web-search operation.

Tool result → evidence → conclusion.

11. VERIFICATION
============================================================

Qwen must not assume success.

Examples:

Create file
→ verify file exists.

Edit code
→ run tests.

Run command
→ inspect output.

Research
→ inspect sources/results.

Create project
→ inspect resulting structure.

If verification fails, continue troubleshooting where appropriate.

============================================================
12. CLARIFICATION
============================================================

If an action is ambiguous and guessing could cause the wrong result, ask.

Example:

"Delete the project."

If multiple projects exist:

"Which project do you want me to delete?"

Do not guess dangerous or irreversible actions.

============================================================
13. SAFETY AND PERMISSIONS
============================================================

The final runtime must use permission and confirmation policies.

Potentially destructive or irreversible operations may require confirmation.

Examples:

- deleting large numbers of files
- destructive terminal commands
- deleting projects
- sending external communications
- financial operations
- irreversible changes

Training must teach Qwen to respect runtime permissions.

Qwen must never attempt to bypass security controls.

14. EIGHT-PHASE QWEN ROADMAP
============================================================

The Qwen project is divided into exactly eight major phases.

Do not skip phases.

Do not silently merge phases.

Do not begin a later phase until the previous phase passes its required gate.

------------------------------------------------------------
PHASE 1 — AGENT SPECIFICATION AND ARCHITECTURE
------------------------------------------------------------

Goal:

Define exactly what the Qwen3-8B agent is supposed to become.

Tasks:

- finalize capabilities
- define agent behavior
- define answer-vs-action behavior
- define tool-use principles
- define NEXUS relationship
- define safety boundaries
- define training architecture
- define runtime architecture conceptually
- define evaluation criteria

Output:

- architecture specification
- capability specification
- behavior specification
- evaluation specification

Gate:

The agent specification must be internally consistent and complete.

Do not train yet.

------------------------------------------------------------
PHASE 2 — DATASET ENGINEERING
------------------------------------------------------------

Goal:

Create the high-quality Qwen agent training dataset.

Dataset must cover:

- NEXUS knowledge
- general reasoning
- NEXUS actions
- filesystem
- terminal
- browser
- web research
- coding
- tool selection
- planning
- multi-tool workflows
- verification
- clarification
- failure recovery
- permissions

Use conversational/tool-call compatible data.

Avoid generic world-knowledge duplication.

Use diverse language.

Avoid memorization.

Perform:

- validation
- deduplication
- leakage detection
- schema validation
- category balancing
- deterministic splitting

Outputs:

- dataset
- dataset manifest
- statistics
- train split
- validation split
- test split

Gate:

Dataset must pass all validation checks.

------------------------------------------------------------
PHASE 3 — TOOL MANIFEST AND SIMULATION
------------------------------------------------------------

Goal:

Define the tools Qwen will learn to interact with.

Create:

- tool schemas
- argument schemas
- tool descriptions
- tool-call examples
- successful tool results
- failure results
- recovery examples
- multi-tool traces

The training tools are simulated representations.

They must NOT execute real system actions during training.

Gate:

All schemas and example traces must validate.

------------------------------------------------------------
PHASE 4 — TRAINING PIPELINE PREPARATION
------------------------------------------------------------

Goal:

Prepare the actual Qwen3-8B fine-tuning environment.

Tasks:

- model loading test
- tokenizer validation
- hardware detection
- quantization compatibility
- LoRA/QLoRA configuration if appropriate
- training configuration
- checkpoint configuration
- reproducibility configuration
- dry-run training
- memory checks
- dataset loading test

Hardware context:

Windows environment.

RTX 3050-class GPU may be limited in VRAM.

Do not assume unlimited GPU memory.

Kaggle GPU may be used for actual training if required.

Do not waste GPU sessions on simple preparation work.

Gate:

The training pipeline must successfully complete a dry run before expensive training begins.

------------------------------------------------------------
PHASE 5 — QWEN3-8B TRAINING
------------------------------------------------------------

Goal:

Actually fine-tune Qwen3-8B.

Requirements:

- preserve checkpoints
- support resume
- record configuration
- record training metrics
- record hardware
- record software versions
- save tokenizer/configuration
- save final model/adapter

Do not modify NEXUS.

Training happens in the isolated Qwen workspace.

Gate:

Training completes successfully and produces a loadable model/adapter.

------------------------------------------------------------
PHASE 6 — EVALUATION AND VALIDATION
------------------------------------------------------------

Goal:

Prove that training actually improved the intended behavior.

Evaluate:

- baseline Qwen3-8B
- fine-tuned Qwen3-8B

Test:

- general reasoning
- NEXUS knowledge
- tool selection
- argument correctness
- multi-tool planning
- verification
- clarification
- failure recovery
- hallucinated execution
- generalization
- retention of general capabilities

Do not evaluate only training loss.

Produce:

- baseline report
- fine-tuned report
- comparison report
- pass/fail result

Gate:

Qwen must demonstrate useful agent behavior.

If it fails:

STOP.

Do not integrate.

THIS PHASE MUST NOT BEGIN UNTIL PHASE 6 PASSES.

Qwen becomes the reasoning/action brain.

Gate:
