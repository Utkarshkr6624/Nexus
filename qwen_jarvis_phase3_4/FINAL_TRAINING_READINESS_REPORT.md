**2. Is the training pipeline ready? Yes (CPU-verified).** Data loader with assistant-only per-turn masking (44 tests), trainer with safe modes and a production lock, checkpoint/resume system, evaluation system, Kaggle notebook and package. 337 automated tests pass; the tiny-model smoke test runs train -> evaluate -> checkpoint -> interrupt -> resume end to end. **Not testable here:** the bitsandbytes 4-bit path, fp16 GradScaler stability on a T4/P100, real VRAM and tokens/s (all PENDING PHASE 5).

**3. Is Qwen3-8B configured correctly? Yes, as far as it can be verified offline.** `Qwen/Qwen3-8B` is the only model (validation rejects any other production `model_id`, `trust_remote_code`, `quant.enabled: false`, `flash_attention_2`, an unofficial tokenizer); architecture, vocabulary, special tokens and chat template were read from the real files and rendered with transformers 5.19.0; QLoRA = NF4 + double quant, LoRA r=16/alpha 32 on all seven projections (43.6 M trainable parameters), lr 1e-4 cosine, 2 epochs, effective batch 16, max length 1024 (0% truncation), chunked label-only loss, gradient checkpointing; precision picks bf16 only on compute capability >= 8 (T4/P100 -> fp16 + GradScaler). Every parameter is documented with a VERIFIED / ASSUMED / ESTIMATED label in `docs/TRAINING_DESIGN.md`. Recommended hardware: T4 (P100 support in Kaggle's default PyTorch wheels is unverified).

## 10. What is NOT verified and what Phase 5 must do first
* **Do not commit the full quota first.** Start with a short run (for example `--set train.max_steps=20`) and read `tok_per_s`, `skipped_steps` and peak memory; compare with the estimates (12.5 GiB peak, 132-397 tokens/s, 2.6-7.8 h for 2 epochs). If memory is tight use the OOM ladder (micro-batch 2 x 8, then 1 x 16).
* Untested on a GPU: 4-bit loading, fp16 numerics (the guard aborts after 20 consecutive skipped steps), the `dtype=`/`torch_dtype=` fallback on older transformers, `save_pretrained` of a 4-bit PEFT model, Kaggle quotas/disk/session limits, library versions (requirements are bounded only above; resolved versions are printed and `pip check` run).
* The guard and fresh-run checks are covered only by CPU tests. The notebook's gate requires a human to set `PHASE5_AUTHORIZED`, `CONFIRM_PRODUCTION` and the unlock environment variable.
* After training: run the evaluation (base vs fine-tuned) before any integration; the NEXUS integration gate in the Phase 1 plan still applies. Nothing in this workspace integrates Qwen into NEXUS.
* Dataset notes for a later version: remove time-sensitive "no training has run" statements, broaden templated families, consider adding open general-purpose replay data (the Phase 1 plan suggests it) to protect general ability.
